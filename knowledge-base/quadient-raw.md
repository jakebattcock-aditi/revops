Salesforce Integration & Automation
Project Gemini - AP-to-Digital Zapier Sync
Built, own, and continue to iterate on a one-way, event-driven, 7-stage chained Zapier pipeline - internally named Project Gemini - that syncs every new Opportunity and its related records (Account, Contact, VAR/partner contacts, Campaign) from the legacy AP Salesforce org into Digital Salesforce (CXM) the moment it's created in AP. The chain runs to roughly 136 individual steps across the 7 stages. Each stage does a scripted find-or-create against Digital rather than a straight record copy, because AP and Digital run materially different data models, picklists, record types and ownership.
Stage-by-stage build:

* Stage 1 - Trigger/Orchestrator (8 steps): Fires on new AP Opportunity; holds a load-bearing 5-minute delay so AP finishes writing the related Account/Contact cascade before downstream stages query it; chains and accumulates return values across all 6 following sub-zaps.
* Stage 2 - Account Process (13 steps): Runs an "Account Value Scripts" code step doing Sales Org → Country/Sub-Region/Region/Digital Sales Org lookups, FTE → Employee Size Range banding, a 35-character SAP name split, and SOQL apostrophe-escaping; searches Digital by three name variants; creates or updates the Account; counts existing New Business Opportunities for Stage 5's logic.
* Stage 3 - Contact Process (14 steps): Three-tier hierarchical contact lookup (Opportunity Contact Role → Account Primary Contact → first Account-Contact Relation); matches into Digital by email.
* Stage 3B - VAR Contact Process (25 steps): Primary partner-contact sync with a four-way branch (VAR Account present / no VAR Account / Sage 50 USA / Sage 50 Canada); matches the Digital account via `AP_SFDC_ID__c`.
* Stage 3C - VAR Secondary Contact Process (19 steps): Added after the original 5-stage design and wired permanently into the chain; same pattern for the secondary VAR contact.
* Stage 4 - Campaign Process (20 steps): A presence check (handles empty/missing/"NO CAMPAIGN" in any casing) replacing an old hardcoded-empty-string bug; on a hit, translates AP Campaign Type to the Digital equivalent before finding-or-creating the Digital Campaign and managing membership.
* Stage 5 - Opportunity Process (37 steps, the largest and most complex stage): Resolves the Digital owner via `Legacy_SFDC2_Id__c`; a single ~15KB JS code step maps AP Record Type → Digital Record Type ID / Solution / Logo Type / Distribution Channel across 4 AP record types; builds the Opportunity name; decides New Business vs. Solution Upsell (or Strategic VAR on Partnership); applies Partner Referral/Sold-To mapping (Sage APA + US/CAD only); resolves the Partner Contact via a VAR Secondary → VAR Primary → null fallback; runs 4 create paths, each with a duplicate guard and an Excel/OneDrive error-log step; creates the Opportunity, an Opportunity Contact Role, and - on 2 of the 4 paths - an Influencer Contact Role.

Salesforce Reporting, Dashboards & Org Structure
Beanpay Admin Dashboard migration (AP → Digital SFDC)
Diagnosed the root architectural cause of a broken dashboard migration: the Implementation object from AP had not been migrated to Digital, with the underlying data landing on the Opportunity object instead - meaning every payment-related report needed rebuilding against Opportunity-object filters rather than a straight rebuild. Root-caused a class of widget errors ("source report is based on a report type inaccessible to the dashboard's running user") down to a custom report type's Deployment Status having been left on "In Development" since November 2023, likely an oversight, rather than "Deployed," and fixed it with a single Setup change. Identified the remaining widget errors as stale field references from the rebuild and deliberately paused remediation pending stakeholder sign-off on filter/field decisions, to avoid remapping the same widgets twice. Surfaced a data-accuracy concern (an implementation-turnaround-time KPI believed inaccurate, suspected to be a start/end date field mapping issue) for stakeholder follow-up.
NCV (Non-Committed Volume) Provider Key workflow
Root-caused a recurring "conflict quotes" issue in the quoting process down to a missing provider key (an alphanumeric SAP-originating identifier linking a customer's payments subscription to billing), and traced exactly where that key lives in Salesforce (on the Contract attached to the Commercial Opportunity, not the NCV Opportunity itself). Documented the full standard resolution workflow and built a rep-facing training session around it, scoping the edge-case path (pre-migration data gaps) to a simple ticket-filing action rather than rep-level investigation. Flagged a system-level enhancement - auto-populating the provider key on NCV quotes - to remove the manual step entirely.
EMEA/NORAM Salesforce role hierarchy restructuring
