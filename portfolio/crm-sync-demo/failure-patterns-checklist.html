8 ways a CRM sync fails without telling you

A sync can run green for months while quietly sending bad data. These are the patterns I look for first, and how to check each one in about ten minutes.

1A placeholder left in a live field

Looks likeA test value typed in while building (a sample headcount, a fixed date) never got swapped for the real field.
Why it hidesNothing errors. Every record just gets the same value.
CheckPull 20 recent records. Is any field identical on all of them?

2A test ID hardcoded in a live step

Looks likeOne step uses a literal record ID instead of a mapped value, so it keeps processing the same record.
Why it hidesThe step succeeds every time, just on the wrong data.
CheckOpen every step. Any value that is not a mapped field is a suspect.

3A match key saved only when a record is created

Looks likeThe source ID is written on create but not on update, so records that already existed never get it.
Why it hidesLater lookups quietly miss those records and create a duplicate or an orphan.
CheckCount the records that are missing the key. It should be zero.

4Searching on a blank value

Looks likeA contact with no email gets searched by email anyway.
Why it hidesA blank search can return nothing, or the wrong record, and neither raises an error.
CheckPut a "does the value exist?" guard in front of every search, and log what it skips.

5Overlapping match conditions

Looks likeAn OR condition that already covers a narrower one, so the narrow rule does nothing and the broad one over-matches.
Why it hidesIt works for most names, then merges two different customers that share a long prefix.
CheckTest with two made-up records that share the first 40 characters of their name.

6Updates that overwrite good data

Looks likeAn update step sends blank or fixed text to a field that already has a real value.
Why it hidesThe record saves fine. The old value is just gone.
CheckRun an update on a record that already has data. Compare the field before and after.

7Defaults that invent data

Looks likeA missing date becomes today, a missing owner becomes a catch-all user.
Why it hidesThe default keeps the sync alive, but reports built on that field are now wrong.
CheckList every default. For each one, ask which report reads that field.

8Leftovers: debug switches and dead outputs

Looks likeDebug logging still on in production, or a flag calculated from the wrong variable that nothing reads yet.
Why it hidesNoisy logs bury real errors. A dead flag is harmless until someone starts relying on it.
CheckSearch for debug switches. For every output, find what reads it.
